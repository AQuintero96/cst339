## General Technical Approach

The application keeps its presentation, business, and persistence responsibilities separate.

Controllers handle requests, validation results, and redirects. Business services handle account authentication, password processing, and preparation of part information. Data services execute SQL through JdbcTemplate.

The business services depend on DAO interfaces. Spring supplies the implementations through constructor injection.

### Registration and Login

AccountDataService inserts registration information into app_users and looks up accounts by username.

AccountService creates a random salt and derives a password hash using PBKDF2 with SHA-256. The algorithm, iteration count, salt, and hash are encoded into the password_hash column.

During login, the service retrieves the stored account and compares the submitted password's derived hash with the stored hash. A successful login creates a session containing the username and first name.

### Part Creation

PartService prepares validated form values and calls PartDataService. The DAO inserts the part and retrieves the ID generated by MySQL.

The create operation is transactional. A runtime failure during the operation causes a rollback. The controller redirects to confirmation only after the service returns successfully.

The confirmation page displays the saved submission. It is not a general-purpose page for retrieving an existing part by ID.

## Key Technical Decisions

| Decision | Reason |
| --- | --- |
| Spring JDBC and DAO interfaces | Builds on Activity 4 and keeps SQL in the persistence layer |
| Separate inventory database | Keeps milestone records separate from the activity's sample orders |
| Constructor injection | Makes each service's dependencies explicit |
| Bound SQL parameters | Keeps data values separate from SQL statements |
| Database-generated identifiers | Replaces the temporary application counter |
| Unique username constraint | Prevents duplicate accounts, including concurrent registration attempts |
| Salted password hashing | Avoids storing plaintext account passwords |
| BigDecimal for unit cost | Matches the database's decimal cost values |
| Transactional part creation | Keeps insertion and generated-ID handling within one transaction |
| DB_PASSWORD environment variable | Keeps the database password out of application.properties |
| Manual schema setup | Makes database creation an explicit, documented step |

## Error Handling

Duplicate usernames return a field error on the registration form. Incorrect login credentials return the existing login error message.

Other database access exceptions propagate from the DAO to the controller. The controller returns the form with an availability message instead of displaying a success confirmation.

The controller logs the exception type without including submitted credentials. These database-outage paths are implemented but were not part of the recorded screenshot tests.

## Known Issues and Limitations

- MySQL 5.7.24 does not enforce the script's CHECK constraints. Java validation checks submitted form values.
- Saved parts cannot yet be browsed, edited, or deleted through the application.
- Spring Security has not yet been integrated, and protected-route enforcement remains future work.
- The part confirmation uses a flash attribute. Refreshing it returns to a new form when the confirmation data is no longer available.
- An empty category can display both the required-field and supported-category messages.
- Automated testing currently consists of the application context test. Functional behavior was checked manually.
- This milestone's screenshots document desktop behavior. Phone and tablet layout evidence remains in the Milestone 3 report.

## Risks and Future Work

A database outage prevents registration, login, and part creation. The application handles those failures, but the database must be running for normal operation.

The schema script creates missing tables but does not change existing table definitions. Future structural changes will need a separate migration.

A connection failure during commit can leave the outcome uncertain to the browser. The part error message avoids claiming that no record was saved. The current form does not provide duplicate-submission protection for every retry scenario.

Bootstrap is loaded from a CDN, so its styles and scripts depend on network access or cached resources.

Milestone 5 will add product display, update, and delete operations. Milestone 6 will add Spring Security.
